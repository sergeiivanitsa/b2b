# Итерация 7 — система фактических сигналов

## 1. Цель

Сформировать из нормализованных фактов `CompanyReport` набор проверяемых
фактических сигналов о статусе компании, её финансовом состоянии и судебной
активности. Сигнал показывает отдельное наблюдение, но не рассчитывает общий
балл, не формирует итоговый вердикт и не оценивает вероятность взыскания.

Правила формирования сигналов должны быть детерминированными: одинаковый
набор нормализованных фактов всегда даёт одинаковый набор сигналов, их поля и
порядок.

## 2. Пользовательская ценность

Пользователь получает прозрачные основания для дальнейшей оценки контрагента:
что в доступных данных говорит о деятельности компании, её финансах и
судебной нагрузке. Каждый вывод можно проверить по конкретным нормализованным
фактам, источнику и периоду, не доверяя непрозрачному скорингу или ИИ.

## 3. Входные данные

Единственный вход системы — нормализованные факты доступных наборов данных
`CompanyReport`:

- `CounterpartyFacts` — статус, даты регистрации и прекращения деятельности;
- `FinanceFacts` — финансовые периоды и показатели отчётности;
- `ArbitrationFacts` — дела, роли компании, статусы и агрегированные итоги.

Система сигналов не обращается к DataNewton, другим HTTP-источникам, БД,
`raw_payload` или ненормализованным ответам провайдера. Статус и
completeness набора данных учитываются только для определения пригодности
фактов и предупреждений; они не заменяют отсутствующие факты.

## 4. Выходная модель Signal

Результат — упорядоченный список объектов `Signal`. Один объект описывает
одно самостоятельное фактическое наблюдение. Один и тот же факт может входить
в основания нескольких сигналов, если у каждого из них своё явно указанное
правило.

`Signal` не является баллом, вероятностью, рекомендацией или итоговым
вердиктом. Значения `strength` и `confidence` характеризуют только силу
правила и полноту его фактического основания соответственно.

## 5. Обязательные поля сигнала

| Поле | Требование |
| --- | --- |
| `code` | Стабильный машинный код правила. Не зависит от текста интерфейса. |
| `category` | Категория из закрытого набора этой итерации. |
| `direction` | Направление влияния отдельного факта; не является общим вердиктом. |
| `strength` | Фиксированная сила сработавшего правила: `low`, `medium`, `high` или `critical`. |
| `factual_basis` | Структурированное, проверяемое основание: использованные нормализованные поля, их значения, сравнение или агрегат, а также идентификаторы периодов или дел, когда они есть. Не содержит raw-ответ провайдера. |
| `source` | Источник нормализованных фактов: соответствующие метаданные `CounterpartyFacts`, `FinanceFacts` или `ArbitrationFacts`. Для нескольких источников указываются все использованные источники. |
| `period` | Период применимости: дата, год, диапазон лет либо состояние «без периода» для статуса компании. |
| `confidence` | `high`, если правило опирается на достаточные и непротиворечивые факты полного набора; `medium`, если основание достаточно, но набор помечен неполным или имеет нерешающие warnings; `low` в этой итерации не даёт права создавать направленный сигнал. |
| `warnings` | Список безопасных предупреждений, перенесённых из использованных нормализованных фактов и дополненных предупреждениями о неполноте или конфликте. Пустой список допустим. |

Значения в `factual_basis` передаются без округления, подмены единиц и
интерпретации пропуска как нуля. Основание должно позволять независимо
воспроизвести результат правила только из нормализованных фактов.

## 6. Категории и направления влияния

Категории текущей версии:

- `legal_status` — юридический статус и срок деятельности;
- `financial` — сведения финансовой отчётности;
- `arbitration` — арбитражная активность и нагрузка.

Направления:

- `positive` — факт, который сам по себе является благоприятным наблюдением;
- `negative` — факт, который сам по себе является неблагоприятным наблюдением;
- `informational` — важный факт без направления для будущего общего вывода.

Направление применяется только к конкретному сигналу. Система не суммирует
направления, не назначает числовой score и не выдаёт формулировки о высокой,
средней или низкой вероятности взыскания.

## 7. Правила формирования сигналов

Все правила применяются только при наличии достаточных нормализованных
фактов. Пороговые значения ниже являются частью версии правил; они не зависят
от порядка входных записей, времени выполнения или ИИ.

| Code | Фактическое условие | Category / direction / strength | Period |
| --- | --- | --- | --- |
| `counterparty.active` | `is_active` явно равно `true`; отсутствует конфликт со сведением о прекращении деятельности. | `legal_status` / `positive` / `medium` | без периода, с датой получения источника |
| `counterparty.dissolved` | `is_active` явно равно `false` либо указана `dissolved_date`; сведения не противоречат друг другу. | `legal_status` / `negative` / `critical` | дата прекращения, если известна |
| `counterparty.long_operating_history` | Нормализованное значение `years_from_registration` составляет не менее пяти полных лет; дата регистрации известна. | `legal_status` / `positive` / `low` | от даты регистрации до даты получения источника |
| `finance.reporting_absent` | Набор `finance` доступен, но в нём отсутствуют финансовые периоды и годы отчётности. Недоступный, не найденный или ошибочный набор не удовлетворяет правилу. | `financial` / `informational` / `medium` | без периода |
| `finance.negative_equity` | В последнем по году периоде с известным `equity` капитал строго меньше нуля. | `financial` / `negative` / `high` | год соответствующего периода |
| `finance.revenue_decline` | В двух последних последовательных годах с известной `revenue` выручка более позднего года строго меньше выручки предыдущего года. | `financial` / `negative` / `medium` | два сравниваемых года |
| `finance.net_loss` | В последнем по году периоде с известным `net_profit` чистая прибыль строго меньше нуля. | `financial` / `negative` / `medium` | год соответствующего периода |
| `finance.cash_shortfall` | В одном и том же последнем по году периоде известны `cash_and_equivalents` и `short_term_liabilities`, причём денежные средства строго меньше краткосрочных обязательств. Сила `high`, если денежные средства составляют менее 25% обязательств, иначе `medium`. | `financial` / `negative` / `medium` или `high` | год соответствующего периода |
| `finance.high_accounts_payable` | В одном и том же последнем по году периоде известны `accounts_payable` и `current_assets`, причём кредиторская задолженность строго больше оборотных активов. | `financial` / `negative` / `high` | год соответствующего периода |
| `arbitration.high_respondent_case_count` | Набор дел полный (`is_complete = true`), а число дел с ролью `respondent` не менее 10. | `arbitration` / `negative` / `high` | период, покрываемый набором дел |
| `arbitration.respondent_case_growth` | Набор дел полный; для двух последних последовательных календарных лет известны количества дел с ролью `respondent`; количество в более позднем году строго больше, а прирост составляет не менее трёх дел. | `arbitration` / `negative` / `medium` | два сравниваемых года |
| `arbitration.open_cases` | Набор дел полный и содержит хотя бы одно дело со статусом `open`. | `arbitration` / `negative` / `medium` | период, покрываемый открытыми делами |
| `arbitration.frequent_plaintiff` | Набор дел полный; число дел с ролью `plaintiff` не менее 10 и строго больше числа дел с ролью `respondent`. | `arbitration` / `positive` / `medium` | период, покрываемый набором дел |

Для выбора «последнего» финансового периода используется наибольший год,
содержащий все показатели, необходимые конкретному правилу. Если одного из
них нет, система может перейти к более раннему периоду только для сигнала,
который не требует сравнения периодов; выбранный год обязательно указывается
в `factual_basis` и `period`. Для сравнения выручки и судебной нагрузки годы
должны быть последовательными; пропуск года не считается отсутствующей
отрицательной динамикой.

Сигналы сортируются по `category` в порядке `legal_status`, `financial`,
`arbitration`, затем по `code` в лексикографическом порядке. Внутри
`factual_basis`, `source` и `warnings` применяется стабильный порядок,
определяемый исходными нормализованными фактами.

## 8. Обработка отсутствующих, неполных и противоречивых данных

Отсутствующее значение никогда не преобразуется в ноль, отрицательный факт
или срабатывание правила. Если для правила не хватает хотя бы одного
обязательного факта, направленный сигнал не создаётся. При необходимости в
результат добавляется безопасное предупреждение о неполноте данных, но оно не
заменяет сигнал и не меняет направление других сигналов.

Недоступный, ошибочный, отключённый, ограниченный тарифом или не найденный
dataset не означает отсутствие финансовой отчётности, дел или статуса
компании. `finance.reporting_absent` создаётся исключительно по успешному
нормализованному набору `FinanceFacts`, который явно не содержит периодов и
годов.

Агрегаты арбитража, зависящие от полного перечня дел, не используются при
`is_complete = false`: не формируются сигналы о большом числе дел ответчиком,
росте нагрузки, открытых делах или частой роли истца. Неполнота отражается в
warnings.

Если факты статуса компании противоречат друг другу (например, действующий
статус одновременно с датой прекращения деятельности), сигналы
`counterparty.active` и `counterparty.dissolved` не создаются. Вместо них
создаётся `counterparty.status_conflict` с категорией `legal_status`,
направлением `informational`, силой `high`, обоими конфликтующими фактами в
`factual_basis` и предупреждением `counterparty_status_conflict`. Конфликт не
разрешается предположением, давностью источника или ИИ.

## 9. Scope

- Детерминированное формирование и сериализация `Signal` из
  `CounterpartyFacts`, `FinanceFacts` и `ArbitrationFacts`.
- Правила и коды сигналов, перечисленные в этой спецификации.
- Проверяемое фактическое основание, источник, период, confidence и warnings
  для каждого созданного сигнала.
- Стабильный порядок результатов.
- Тесты правил, отсутствующих и неполных данных, противоречий и
  детерминированности.

## 10. Out of scope

- Общий числовой score, агрегация направлений и итоговый вердикт.
- Оценка вероятности взыскания в любой шкале.
- Использование ИИ, генеративных моделей или эвристик, основанных на тексте
  raw-ответов.
- Новые внешние HTTP-вызовы, изменения provider layer и нормализаторов.
- Хранение `raw_payload`, новых данных в БД, миграции и новые API endpoints.
- Сигналы по `TaxFacts`, `FsspFacts`, `BankruptcyFacts` и иным источникам,
  отсутствующим в текущем `CompanyReport`.
- UI, объяснительный текст для пользователя и рекомендации действий.

## 11. Критерии приёмки

- [ ] Система принимает только нормализованные `CounterpartyFacts`,
  `FinanceFacts` и `ArbitrationFacts` из `CompanyReport`; HTTP, БД и
  `raw_payload` не используются.
- [ ] Каждый созданный сигнал содержит все девять обязательных полей и
  проверяемое `factual_basis`.
- [ ] Реализованы все коды и условия из раздела 7, включая стабильные пороги
  и порядок сигналов.
- [ ] Одинаковые нормализованные входы дают идентичные сигналы, поля,
  warnings и порядок.
- [ ] Пропущенные, недоступные и ошибочные данные не интерпретируются как
  нули или отрицательные факты.
- [ ] Неполный перечень арбитражных дел не создаёт сигналы, требующие полного
  агрегата.
- [ ] Противоречащие сведения о статусе не создают одновременно сигналы
  «компания действует» и «компания ликвидирована».
- [ ] Не появляются общий score, итоговый вердикт, вывод о вероятности
  взыскания или результат работы ИИ.
- [ ] Production-код, API-контракты, миграции и provider layer в рамках
  подготовки этой спецификации не изменяются.

## 12. Обязательные тестовые сценарии

- Действующая компания с непротиворечивым статусом создаёт
  `counterparty.active` с фактами статуса и метаданными источника.
- Ликвидированная компания с известной датой прекращения создаёт
  `counterparty.dissolved`; действующий и ликвидированный статус одновременно
  не создаются.
- Компания, зарегистрированная не менее пяти полных лет назад, создаёт
  `counterparty.long_operating_history`; неизвестная дата регистрации — нет.
- Успешный пустой `FinanceFacts` создаёт `finance.reporting_absent`; ошибка,
  `not_found`, отключённый или отсутствующий набор — не создаёт.
- Отрицательный капитал, убыток, снижение выручки, недостаток денежных
  средств и высокая кредиторская задолженность создаются только при точном
  выполнении соответствующих условий и с верным годом в основании.
- Нулевое, отсутствующее или неполное значение любого нужного финансового
  показателя не подменяется отрицательным значением и не создаёт сигнал.
- Снижение выручки при пропущенном промежуточном годе не создаётся; равные
  значения также не считаются снижением.
- Полный набор дел с пороговым числом ответных дел, ростом нагрузки,
  открытыми делами и преобладающей частой ролью истца создаёт соответствующие
  сигналы с проверяемыми агрегатами и периодами.
- Такие же арбитражные факты при `is_complete = false` не создают сигналы,
  требующие полного списка, и возвращают предупреждение о неполноте.
- Противоречивые факты статуса создают только
  `counterparty.status_conflict` с обоими значениями в основании.
- Перестановка входных фактов, периодов, дел и warnings даёт одинаковый
  упорядоченный результат.
- Ни один сценарий не создаёт общий score, итоговый вердикт или текст о
  вероятности взыскания.

## 13. Риски и открытые вопросы

| Риск или вопрос | Контроль / решение | Блокирует реализацию |
| --- | --- | --- |
| Доступные на текущем тарифе источники ограничены тремя наборами. | Scope ограничен текущими нормализованными фактами; Tax, FSSP и банкротство добавляются отдельной итерацией после probe и нормализации. | Нет |
| Провайдер не фиксирует единицы финансовой отчётности. | Использовать только сравнения показателей одного периода и не применять абсолютные денежные пороги. | Нет |
| Арбитражный ответ может быть неполным. | Все правила, использующие полные агрегаты дел, требуют `is_complete = true`. | Нет |
| Пороги 5 лет, 10 дел, прирост 3 дела и 25% денежных средств требуют продуктового подтверждения перед реализацией. | Зафиксировать их как версию ruleset либо изменить отдельным согласованным решением с обновлением тестов. | Да |
| Семантика отсутствия отчётности может отличаться между вариантами успешного ответа provider. | Подтвердить на fixtures нормализатора, что успешный пустой набор однозначно отделён от ошибки, `not_found` и недоступности. | Да |
